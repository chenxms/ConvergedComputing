# 批次全流程增强汇聚实施方案

## 1. 背景与目标
- 现状：批次 G7-2025 在“清洗→区域汇聚→学校汇聚”链路上耗时约 80 分钟，遇到缺失数据时会回退到基础结构，导致增强字段缺失。
- 目标：
  - 所有学校和科目必须产出增强字段（百分位、区分度、等级占比、维度与学校排名、问卷题目占比等），禁止回退基础结构。
  - 将全流程耗时压缩到 12–20 分钟，满足批量调度要求。
  - 提供前置校验与异常兜底，便于排查缺失数据。

## 2. 总体方案概述
1. 启用 v1.2 SubjectsBuilder：覆盖旧版 builder，启用维度与学校排名缓存及增强字段拼装。
2. 强化 CalculationService：复用一次性加载的数据、取消空数据 fallback，缺失即抛错。
3. 优化脚本流程：提升并发、确保缓存生效、增加增强字段断言。
4. 完善前置校验：在跑批前校验清洗结果、问卷分布及维度 JSON 完整性。
5. 数据库支持：补充关键索引，提升并发查询效率。

## 3. 详细实施步骤
### 3.1 环境准备
- 备份现有文件：
    cp app/services/calculation_service.py app/services/calculation_service.py.bak
    cp app/services/subjects_builder.py app/services/subjects_builder.py.bak
- 导出当前批次统计结果（必要时回滚）：
    mysqldump --single-transaction       --tables statistical_aggregations       --where="batch_code=G7-2025" > backup_G7_2025_stats.sql

### 3.2 启用 v1.2 SubjectsBuilder
- 将 deployment_package_production/app/services/subjects_builder.py 拷贝至 app/services/subjects_builder.py。
- 确认 build_regional_subjects_v12、build_school_subjects_v12、bbuild_dimension_rank_cache、reset_cache_stats、get_cache_stats 可用。
- 删除或禁用旧版 build_school_subjects 中回退基础结构的逻辑，所有调用统一走 v1.2 版本。

### 3.3 重构 CalculationService
- consolidate_multi_subject_results：遇到空 subject_data_df 或百分位、区分度、等级分布计算失败时直接抛出 ValueError；precomputed_dimension_stats 需覆盖所有科目。
- calculate_subject_dimensions：改为接受预加载的 scores_df 切片，不再每科调用 get_student_scores；若维度 JSON 或问卷回退聚合为空，直接抛错；成功结果写入缓存供学校阶段复用。
- save_regional_statistics / save_school_statistics：捕获 builder 异常后立即抛出，不再回落基础版本；写入前断言增强字段存在（百分位、区分度、维度列表、排名等）。

### 3.4 脚本调整
- scripts/rebuild_school_v12.py：复用 all_scores_df，失败时终止；调整 REBUILD_CONCURRENCY 默认值为 4；调用 builder.bbuild_dimension_rank_cache(batch_code) 并传入 build_school_subjects_v12；写库前断言增强字段完整。
- run_full_batch_pipeline.py：清洗后校验 student_cleaned_scores 是否覆盖所有学校与科目，以及 questionnaire_option_distribution、question_dimension_mapping 是否存在；校验失败直接中断并输出缺失列表。

### 3.5 数据库索引优化
    ALTER TABLE student_cleaned_scores
      ADD INDEX idx_batch_subject_school (batch_code, subject_name, school_code);

    ALTER TABLE questionnaire_question_scores
      ADD INDEX idx_batch_subject_school_q (batch_code, subject_name, school_id);

    ALTER TABLE questionnaire_option_distribution
      ADD INDEX idx_qod_batch_subject_question (batch_code, subject_name, question_id);

### 3.6 校验与上线流程
1. 测试环境执行：docker exec converged-computing-app bash -lc "python run_full_batch_pipeline.py G7-2025"。
2. 使用 scripts/verify_enhanced_fields.py 或自定义 SQL 校验增强字段：所有科目必须包含百分位、区分度、等级分布及维度排名；问卷科目需补齐题目或维度选项占比。
3. 记录区域阶段和学校阶段耗时，目标分别为 8–12 分钟和 8–15 分钟。
4. 验证通过后部署至生产环境，并在首轮执行中实时监控日志与数据库状态。

## 4. 错误处理与回滚
- 若脚本抛出增强字段缺失错误，应排查清洗数据、问卷映射以及缓存构建情况。
- 如需紧急回滚，可还原备份文件 *.bak，并执行数据库备份文件恢复指定批次。

## 8. 清洗阶段预计算方案评估
- 现状诊断：app/services/subjects_builder.py 中 _compute_subject_metrics、_compute_school_rankings 等函数在汇聚阶段对 student_cleaned_scores 反复聚合；维度排名由 build_dimension_rank_cache 在内存中一次性构建；增强指标由计算引擎基于 pandas 计算。
- 可前移的字段：
  - 科目核心指标（均值/方差/最大值/最小值/score_rate 或 difficulty、满分），行量≈科目数，可在清洗收尾落库（建议 subject_core_metrics）。
  - 区域学校排名及总校数，行量≈科目×学校，可落库为 subject_school_rankings 并供学校级复用。
  - 其他现有缓存（区域名次、学校维度缓存）可直接读取上述两张表，减少汇聚阶段 SQL。
- 暂不前移的字段：
  - 维度排名：需拆解 dimension_scores JSON 才能持久化，清洗链路改造大，收益有限，保持在构建缓存阶段执行。
  - 百分位/区分度/等级分布等增强指标：仍由计算引擎统一生成，避免在清洗阶段重复 pandas 计算及失败场景扩散。
- 实施要点：
  1. 在清洗作业末尾新增预聚合步骤，写入 subject_core_metrics(batch_code, subject_name)、subject_school_rankings(batch_code, subject_name, school_code)，并记录批次版本与生成耗时。
  2. 补充索引：subject_core_metrics(batch_code, subject_name)、subject_school_rankings(batch_code, subject_name, school_code)；若落库逻辑为“先删后写”，需保证事务隔离。
  3. 汇聚服务改为优先读取新表，同时保留校验：若记录缺失则终止流程并提示缺表/批次。
  4. 监控扩展：在跑批监控中增加预聚合耗时、写入行数、异常日志，确保问题可快速定位。
  5. 验证流程：先在影子批次压测预聚合的 SQL，确认索引及写入耗时后再推广到生产批次。
- 预期收益：削减汇聚阶段对 student_cleaned_scores 的 N 次聚合 SQL，区域+学校构建时间预计额外下降 10%–15%，同时保留增强指标统一计算带来的可维护性。

## 9. 第一阶段实施计划（2025-09-17 夜间执行）
- 范围聚焦：仅针对 G7-2025 批次启动“强制增强+清洗前置”改造，确保今晚运行的汇聚即刻生效，后续批次按同样流程复制。
- 强制增强落实：
  1. 移除 CalculationService._save_regional_statistics/_save_school_statistics 中的 fallback 分支，SubjectsBuilder 失败即抛错；补充关键日志字段，定位缺失数据。
  2. 巡检 scripts/run_full_batch_pipeline.py、scripts/rebuild_school_v12.py 等入口，统一调用 build_regional_subjects_v12/build_school_subjects_v12，并去除任何 build_regional_subjects 基础版本兜底。
  3. 在 tests/test_v12_* 场景中增加断言：区域/学校 subjects 不得缺失 percentiles、discrimination、grade_distribution、rank 等增强字段。
- 清洗前置落库：
  1. 在清洗收尾脚本增加 subject_core_metrics、subject_school_rankings 两张表的生成与写入，包含批次/科目/学校关键字段及统计值。
  2. 新增/复用索引：subject_core_metrics(batch_code, subject_name)、subject_school_rankings(batch_code, subject_name, school_code)，并封装幂等写入（先删后写）。
  3. 汇聚阶段改读新表，仍保留缺失校验，缺失时阻断流程并提示缺表/缺批次。
- 即刻提效措施：
  - 复用清洗阶段导出的表，CalculationService 构建 subjects 时只做增强字段拼装与 JSON 整理，避免重复统计 SQL，预计汇聚阶段额外下降 10%–15%。
  - builder.build_dimension_rank_cache 改为先检查 subject_school_rankings 是否可复用区域均分；未落库的维度排名仍维持内存缓存，避免首批次改动风险。
  - 调整脚本默认并发：REBUILD_CONCURRENCY=4，配合数据库连接池监控，必要时在配置文件降档。
- 验证与回归：
  1. 影子库先执行一次 run_full_batch_pipeline.py，确认增强字段完整、预聚合表行数与学校/科目匹配。
  2. 记录转换前后区域/学校阶段耗时，目标区域 ≤ 12 分钟、学校 ≤ 15 分钟。
  3. 失败处理：所有 fallback 被去除后，一旦抛错需及时定位数据缺口；排查完毕可重跑，无需回滚基础版本。
- 交付物：今晚实施结束需提交执行记录（命令日志）、预聚合表样例、汇聚输出 diff 与耗时对比，为明日迭代提供基线。
