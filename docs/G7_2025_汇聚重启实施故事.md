# G7-2025 汇聚重启实施故事（Pipeline Relaunch）

- 文档类型：实施故事（PM）
- 版本：v1.2
- 目标批次：G7-2025
- 关联脚本：`scripts/install_g7_guard.py`、`python run_full_batch_pipeline.py`
- 关联服务：`app`（主汇聚）、`subjects`
- 作者：PM
- 发布日期：2025-09-20

---

## 一、背景与问题陈述

- 历史版本的 G7 自动汇聚逻辑仍在服务器运行，若直接放开写入将重新触发旧流水线，导致 G7-2025 批次被重复汇聚、数据不断被覆盖。
- 为阻断异常写入，我们在 `app` 与 `subjects` 容器内运行 `docker compose exec <service> python scripts/install_g7_guard.py`，数据库层已存在 INSERT/UPDATE 触发器，当前禁止任何 G7-2025 的写入。
- 新版全流程脚本 `python run_full_batch_pipeline.py` 已完成重构，需要重新生成 G7-2025 的目标数据，且必须在受控窗口内释放守卫，避免旧逻辑“抢写”。

---

## 二、目标与范围

- **目标**：在受控窗口内完成新版 G7-2025 批次的全量汇聚，交付符合业务口径的数据集，并确保旧逻辑不再对 G7-2025 产生写入。
- **范围**：数据库守卫策略调整、旧流程隔离、`run_full_batch_pipeline.py` 执行与监控、数据校验与收口动作。
- **非范围**：
  - 不涉及新增指标或结构调整；
  - 不包含对其他年级批次的影响评估；
  - 不包含旧流水线的彻底删除，仅停用相关入口。

## 四、前置条件与维护窗口

- **前置清单**
  - 已梳理触发旧汇聚的接口/定时任务清单，并可在窗口前停用；
  - 确认 `run_full_batch_pipeline.py` 本地自测通过，依赖配置在目标环境就绪；
  - 预备专用数据库账号（仅新流水线使用），或确认触发器可识别白名单用户（为后续演进做准备）；
  - 补齐预检查脚本：`check_no_active_old_pipeline`、`check_db_locks`、`check_disk_space`、`backup_G7_2025_stats_clean.sql`；
  - 提前准备对账脚本与查询语句，便于执行后立即校验；
  - 双人复核触发器变更计划、快速回滚脚本（如 `quick_remove_g7_guard.sql`、`scripts/uninstall_g7_guard.py`）与恢复命令。

- **维护窗口建议**
  - 选择业务低峰（建议工作日晚 22:00–24:00），总时长预估 1 小时（含缓冲 30 分钟）；
  - 设定 T0 起点，按“准备 → 守卫调整 → 新流程 → 验收 → 收口”顺序执行；
  - 如遇阻断或超时，T0+30min 内必须决策：继续排查或立即回滚并改期。

## 五、实施步骤

### 1. 准备阶段（T0 前）
- 停止旧版自动汇聚入口：
  - 暂停相关容器内的定时任务或服务守护进程；
  - 若存在人工触发脚本，通知相关团队冻结操作；
  - 必要时将旧入口脚本改为 no-op（留存备份）。
- 执行预检查：
  - `check_no_active_old_pipeline()` 确认旧流水线无存活进程；
  - `check_db_locks()`、`check_disk_space()` 保障资源充足；
  - `backup_G7_2025_stats.sql` 导出关键数据作为回滚基线。
- 启动实时监控：配置数据库写入监控、应用日志采集（`tail -f` + `grep G7-2025`），并记录吞吐、错误率、内存占用、异常写入四类指标，触发异常后可执行 `ultimate_stop.py` 紧急停机。
- 复核守卫回滚方案：记录触发器名称、删除与重建 SQL，确保秒级回滚能力，并准备 `quick_remove_g7_guard.sql` / `scripts/uninstall_g7_guard.py` 等脚本随时调用。

### 2. 守卫策略调整（T0）
- 本次窗口仍以触发器全局拦截为主，操作顺序为“停旧 → 移除守卫 → 跑新 → 验收 → 恢复”。
- 方案首选：修改触发器逻辑，仅放行“新流水线专用 DB 用户”，其他连接继续拦截（若数据库支持 `application_name` 白名单，可视为中期演进试点）。
- 备选方案：完全移除触发器，仅在维护窗口内操作。
  - 需双人确认并记录操作时间，以便审计。
- 在调整完成后，通过试写 SQL 验证：
  - 新流水线账号对 G7-2025 可写入；
  - 普通账号依旧收到触发器拦截错误。

### 3. 新流程运行（T0+10min）
- 切换到部署节点，执行：
  ```bash
  # 方案A：使用包装器脚本（推荐，支持 --batch 和 --env 参数）
  python run_g7_pipeline_wrapper.py --batch G7-2025 --env production

  # 方案B：直接使用原始脚本（兼容模式，仅位置参数）
  python run_full_batch_pipeline.py G7-2025
  ```
  > **注意**：`run_g7_pipeline_wrapper.py` 是新增的包装器脚本，支持命令行参数。原始脚本 `run_full_batch_pipeline.py` 仅支持位置参数。
- 实时监控：命令输出、日志文件、数据库活跃会话（确认仅新流程账号写入），并记录时间线，为断点续传能力预留数据。
- 若监测到旧逻辑写入痕迹：
  - 立即终止流水线执行；
  - 恢复触发器原状；
  - 记录时间戳与写入来源，启动异常定位。

### 4. 数据验证（T0+40min）
- 校验维度与指标：
  - 对比关键指标（总人数、平均分、等级分布、问卷指标等）；
  - 执行预设 SQL / 脚本，与历史期望表进行 diff；
  - 核查核心 API（区域、学校、问卷）返回结构与数值。
- 输出 QA 验收记录：
  - 使用 `docs/templates/validation_report.md` 模板填写验收记录；
  - 标注校验数据来源、标准值、结果与结论。
  > **注意**：验收报告模板已创建在 `docs/templates/validation_report.md`，包含完整的验收检查项。

### 5. 收口与复盘（T0+60min）
- 决策是否保留守卫：
  - 若旧流程全部下线，可移除触发器并更新运维文档；
  - 若需长期防护，将触发器改为白名单模式并启用监控告警。
- 更新文档：
  - 记录本次操作步骤、时间线、参与人；
  - 更新汇聚运维手册、DB 守卫配置说明；
  - 产出复盘（包含风险与后续动作）。
- PM 汇总并向业务方同步：
  - 数据上线时间、校验结果、残留风险；
  - 制定 24 小时内的监控计划与责任人。

## 六、验收标准

1. **写入安全**：维护窗口外，除了新流水线账号，任何连接对 G7-2025 的 INSERT/UPDATE 会被触发器阻断。
2. **汇聚成功**：`run_full_batch_pipeline.py` 正常结束，关键日志无异常或失败重试。
3. **数据一致性**：
   - 与目标口径比对全部通过；
   - 核心指标与预期偏差在 ±0.5% 内或有明确解释。
4. **接口校验**：
   - `/api/v12/batch/G7-2025/regional`、`/api/v12/batch/G7-2025/school/{school_code}`、`/api/v12/batch/G7-2025/questionnaire` 等接口响应正常；
   - 返回结构符合现有 schema，无缺失字段。
5. **运维交付**：文档更新、监控策略上线、回滚方案留存。
