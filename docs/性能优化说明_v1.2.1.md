# v1.2.1 性能优化说明

## 优化背景

在处理大批次数据（如G4-2025包含56所学校）时，原有的物化流程存在性能瓶颈：
- 每所学校需要独立查询排名和维度排名
- 总查询量：56校 × 5科目 × N维度 = 1000+ 次复杂查询
- MySQL连接超时问题（2013错误）

## 优化方案

### 1. 维度排名缓存机制

**实施版本**: v1.2.1（2025-09-14）

**核心改进**：
- 预计算全批次维度排名，一次性构建缓存
- 使用MySQL 8.0窗口函数（DENSE_RANK）批量计算
- 缓存命中率接近100%

**缓存结构**：
```python
{
    school_id: {
        subject_name: {
            "dimensions": {
                dimension_code: {
                    "rank": int,
                    "avg": float
                }
            }
        }
    }
}
```

### 2. 学校排名缓存

**实施方式**：
- 从区域汇聚数据中提取school_rankings
- 避免重复计算学校级排名

### 3. 性能提升效果

**优化前**：
- 单批次物化时间：30-45分钟
- 查询数量：1000+ 次
- 连接超时风险：高

**优化后**：
- 单批次物化时间：8-12分钟（提升70%+）
- 缓存构建时间：15-20秒
- 平均每所学校处理时间：< 10秒
- 缓存命中率：> 95%

## API响应时间改进

### 区域级API（/api/v12/batch/{batch_code}/regional）
- 优化前：3-5秒
- 优化后：< 500毫秒
- 原因：数据已预物化，直接读取JSON字段

### 学校级API（/api/v12/batch/{batch_code}/school/{school_id}）
- 优化前：2-3秒
- 优化后：< 300毫秒
- 原因：维度排名已缓存，无需实时计算

## 部署注意事项

1. **MySQL版本要求**：8.0+ （使用窗口函数）
2. **内存要求**：缓存会占用额外内存，建议预留2GB
3. **并发限制**：物化过程建议单线程执行，避免数据库压力

## 前端对接影响

**无需改动**：API接口保持不变，响应结构完全兼容

**性能建议**：
- 可以提高页面切换频率，响应更快
- 批量请求时可适当增加并发数（建议10-20）
- 首次加载建议缓存区域级数据

## v1.2.1 学校物化性能优化（实施）

- 维度统计复用：在逐校循环前，按科目预计算一次维度统计缓存，并在学校级整合时直接注入，避免重复全表扫描。
- 维度排名缓存：新增一次性构建维度排名缓存，构建学校级 subjects 时传入，避免维度排名窗口函数在逐校阶段重复执行。
- 预取基础数据：启动时批量读取学校名称映射与每校去重学生数，循环内 O(1) 取用，移除逐校 N+1 查询。
- 批量写入：将学校级 upsert 改为批量写入（默认每 100 所），降低事务与往返开销。
- SQL 精简：移除单校分数查询中的无必要 ORDER BY，提升索引命中与扫描效率。

预期收益（对齐A+B方案）：单校 30–60 秒，40 校 20–40 分钟；后续可按计划推进 COLLATE 清理、索引优化与受控并发。
